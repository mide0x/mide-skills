# Skill dictionary

One line per skill on when to reach for it. Helper skills that cannot be invoked are left out. Regenerated by `pick`, `add`, and `dictionary`. Do not edit by hand.

## /architect
Use it when
About to start a piece of work big enough that jumping straight into code would lock in the wrong structure, and want the shapes designed and compared first.

## /arena
Use it when
Facing a non-trivial piece of work where a single first attempt would likely settle on the wrong shape, and several independent tries could be compared and combined instead.

## /blast-radius
Use it when
Have a small, suspicious change and need to know what it could quietly break elsewhere, with the key safety assumption proven by running real code, not just argued.

## /bro
Use it when
Just read a reply full of technical terms and want the same point said again simply, the way one person would explain it to another.

## /codex-first
Use it when
You want claude to use codex as a subagent

## /create-verification-skill
Use it when
Working on a project that has no scripted way to launch the app, exercise a feature like a real user, and capture proof it worked.

## /deslop
Use it when
Just finished a branch with AI-written code and want the leftover clutter, needless comments, and defensive noise stripped out before review.

## /explain
Use it when
Staring at a piece of code, a type, or a design decision that still doesn't make sense and want it taught until it clicks, with a working example.

## /fix-merge-conflicts
Use it when
A branch has merge conflicts and you want them resolved carefully and checked with a build and tests before moving on.

## /how
Use it when
Trying to understand how part of a codebase works, where a piece of code should live, or what's wrong with its structure, before changing anything.

## /interrogate
Use it when
Finished a code change and want several independent reviewers to attack it from different angles before you trust it, with their findings weighed into one verdict.

## /maintain-verification-skill
Use it when
The app has changed since its testing guide and feature list were written, and you want them checked against the real code and a live run, then fixed.

## /no-comments
Use it when
Finished a change and want an outside eye to strip out unneeded comments, fix what they were papering over, and turn real constraints into enforced checks.

## /poteto-mode
Use it when
Starting a multi-step coding task and want a disciplined default working style, with planning, delegation, verification, and clean writing built in from the first step.

## /recall
Use it when
Coming back to a piece of work after a break and needing to know what you did, what's still open, and what to do next before touching anything.

## /show-me-your-work
Use it when
Doing a long or unattended job that someone else will check afterward and want to see what was decided, why, and on what evidence.

## /tdd
Use it when
Fixing a bug that has a cheap, obvious test target, or someone has explicitly asked for a failing test before the fix.

## /technical-writing
Use it when
Writing or reviewing documentation, a readme, a design proposal, a pull request description, or a commit message and want every sentence clear on a tired engineer's first read.

## /typescript-best-practices
Use it when
Reading or editing a TypeScript file and want its types shaped so invalid data can't be built, cast, or slip in unchecked at the edges.

## /unslop
Use it when
Finished a draft or any piece of writing and want the machine-sounding phrasing stripped out so it reads like a person wrote it.

## /what-did-i-get-done
Use it when
Need a short status update of what you personally shipped in a given stretch, like yesterday or last week, pulled from your own commits.

## /why
Use it when
Wondering why a piece of code was built a certain way, what tradeoffs or past incidents shaped it, and want the answer backed by cited history rather than guesses.
